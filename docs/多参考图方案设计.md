# 多参考图支持方案设计（结合现有「风格母版」+ 网页生成 PPT 流程）

> 版本：v1.0 设计稿 ｜ 状态：**仅设计，不含实现** ｜ 日期：2026-09-12
> 适用代码：`app.py` / `static/index.html` / `chart_renderer.py`

---

## 1. 目标与非目标

### 1.1 目标
1. 把现有「③ 风格母版 / 锁长相」的**单张参考图**能力，升级为**多张参考图**（Multi-Reference）。
2. 每张参考图可**分配角色**（风格 / 人物 / 版式 / 素材 / 自定义）与**权重**，生成时按角色合成结构化指令。
3. 多张参考图能**贯穿网页生成 PPT 的完整链路**：全局默认 → 单页覆盖 → 首图自动母版，最终落到 `④ 页面生图 → ⑤ 生成 PPTX`。
4. 对中转站兼容性做**能力探测 + 分级降级**，保证"即使中转站只支持单图"也能用。
5. 兼容存量数据：老的历史记录（`refImage` 单图）可无损迁移。

### 1.2 非目标（本期不做）
- 不做参考图的**局部重绘/蒙版编辑**（mask 仍不支持，仅保留接口位）。
- 不做在线图库联网下载、不做以图搜图。
- 不做参考图自动视觉识别（DeepSeek 为纯文本模型，无法读图；如需自动归纳风格需接入多模态模型，列为 P3 可选）。

## 2. 现状梳理（代码级）

| 层 | 位置 | 现状 | 局限 |
|---|---|---|---|
| 前端状态 | `index.html` `state.refImage` / `state.refUrl` | 单张，字符串 | 只能 1 张；无角色、无权重、无启用开关 |
| 前端上传 | `uploadRef()` + `<input id="refFile">` | 单文件选择 | 不支持多选/拖拽/批量 |
| 前端渲染 | `renderRef()` / `setMaster()` / `clearRef()` | 单张预览 + 移除 | 无列表、无排序、无库管理 |
| 自动母版 | `auto_master` 开关 + `generateAll()` 首图逻辑 | 首图成功后写入 `state.refImage` | 只能 1 张，且与手动上传互斥 |
| 后端上传 | `POST /api/upload_ref` | 单 `file` → 存 `masters/`，命名 `ref_<ts>.<ext>` | 单文件；无索引、无去重 |
| 后端生成 | `POST /api/generate` → `ref_image` 字段 | 命中则走 `_gen_edit()` | 字段为单值 |
| edits 调用 | `_gen_edit()` | `files = {"image": (name, bytes, mime)}`，单张 | **只发一张**；字段名固定 `image` |
| 锁定指令 | `_LOCK_STYLE` / `_LOCK_FACE` | 二选一，拼在 prompt 尾部 | 无法按"每张图"分别说明 |
| 存储 | `_save_dirs()` → `<images_dir>/masters/` | 母版/参考图统一目录 | 无元数据文件，无法区分角色 |
| 历史记录 | `captureSnapshot()` / `doRestoreHistory()` | `schemaVersion: 1`，存 `refImage`/`refUrl` | 结构需升级 |

**核心瓶颈**：`_gen_edit()` 的 multipart 只构造了一个文件字段；前端只有一个字符串。整条链路是"单值"假设。

## 3. 技术能力底座（已验证事实）

依据 OpenAI Images API 官方参考与社区实践：

1. **`POST /images/edits` 支持多张输入图**：GPT Image 系列（`gpt-image-1` / `1-mini` / `1.5` / `gpt-image-2` / `chatgpt-image-latest`）**最多 16 张**，每张 `png/webp/jpg` 且 **< 50MB**。`dall-e-2` 仅 1 张。
2. **multipart 传参**：同一字段名重复提交多张图即可（官方 SDK 内部即按 `image` 数组发送；社区示例用 `image[]`）。**数组顺序 = 模型眼中的序号**。
3. **JSON 传参（备选）**：`images: [{file_id | image_url}]`，同样最多 16 张。
4. **提示词按序号引用**：官方示例 `"The first image is me… The second image is…"` —— 这是多参考图绑定的**唯一稳定语义**。
5. **`input_fidelity`**：`high / low`，控制对输入图（尤其面部特征）的还原力度，`gpt-image-1/1.5` 及以后支持，**high 会增加费用**。锁长相/锁风格应显式设为 `high`。
6. **prompt 上限 32000 字符**（GPT Image），足够容纳参考图清单说明。
7. **中转站差异风险**：不同中转站对 multipart 字段名（`image` / `image[]`）、是否允许重复字段、是否透传多图的支持度不一致，且大多**不支持 JSON+file_id**（需要先上传 File API）。→ 必须有探测与降级。

> 结论：多图能力在协议层是**可行且原生支持**的；工程复杂度主要来自**中转站兼容**与**角色语义编排**。

## 4. 总体设计

### 4.1 核心概念：参考图集（Reference Set）

```
ReferenceSet（参考图集）
└── ReferenceImage[]（有序数组，顺序即模型编号 1..N）
    ├── id         前端本地唯一 id
    ├── filename   落盘文件名 ref_<ts>_<n>.<ext>
    ├── url        /api/image/<filename>
    ├── role       style | character | layout | element | custom
    ├── weight     1~5（同一角色的多张图用于排序/取舍）
    ├── enabled    是否本次参与生成
    └── note       自定义说明（role=custom 时必填）
```

### 4.2 角色枚举与指令映射

| role | 中文名 | 注入给模型的指令（英文，写入 prompt 清单块） |
|---|---|---|
| `style` | 风格母版 | 复刻其整体视觉风格：配色、背景质感与色调、字体气质、装饰母题、版式骨架、光影与留白 |
| `character` | 人物/主体 | 保持人物（或主体对象）的脸型五官、发型、服装、比例与该图完全一致 |
| `layout` | 版式骨架 | **仅**参照其构图分区与元素占比（标题/正文/图形区），**不**复制其配色与文字 |
| `element` | 素材元素 | 复用图中所示的具体物件/图标/插画作为素材 |
| `custom` | 自定义 | 原样使用用户在 `note` 中填写的说明（中英不限） |

### 4.3 三级作用域（优先级从低到高）

```
① 全局默认参考图集  →  state.refImages[]        （③ 卡片维护，整批生效）
② 单页覆盖          →  page.refImages (可选)     （④ 每页可指定专属参考图，留空继承全局）
③ 首图自动母版      →  auto_master 生成后追加为 role=style、weight=5 的一张
```

> 合并规则：`单页覆盖 > 首图自动母版 > 全局默认`。冲突时按 **role 去重 + weight 高者胜**（见 §5.2）。

### 4.4 数据流

```
[③ 多图上传/库选] ──┐
                    ├─→ 参考图集(有序+角色) ──┐
[④ 单页覆盖] ───────┘                        │
                                             ▼
                              [生成时装配器 build_ref_payload()]
                                             │
                        ┌────────────────────┴────────────────────┐
                        ▼                                         ▼
             能力探测：中转站支持多图？                    prompt 清单块合成
                        │                                         │
        ┌───────────────┼───────────────┬──────────────┐          │
        ▼               ▼               ▼              ▼          │
   L1 原生多图      L2 拼贴单图      L3 仅主图     L4 串行链式     │
   重复 image[]     2x2 拼合画布     取 weight 最高   逐张 edit     │
        └───────────────┴───────────────┴──────────────┘          │
                        │                                         │
                        └──────────────► /images/edits ◄──────────┘
                                             │
                                      页面图 page_*.png
                                             │
                                     [⑤ /api/build_ppt] → .pptx
```

## 5. 关键设计：提示词合成

### 5.1 参考图清单块（Reference Manifest）

在**用户页面 prompt 之前**插入一段结构化清单，让模型明确每张图的职责：

```
Reference images are provided in order; follow each one according to its role:
1. STYLE MASTER — reproduce the overall visual style of image 1: exact color palette,
   background texture and tone, typography feel, decorative motifs, layout grid,
   lighting and whitespace.
2. CHARACTER — keep the face, hairstyle, clothing and body proportions of the
   character in image 2 identical.
3. ELEMENT — reuse the object/icon shown in image 3 as an illustration asset.
Do NOT copy any text, logo or watermark from the reference images.
Follow the required fidelity: high.
```

中文文案（页面要渲染的文字）仍按现有规则放在正文，**不受清单块影响**，中英混排规则不变。

### 5.2 冲突消解规则

| 场景 | 处理 |
|---|---|
| 多张 `style` | 取 `weight` 最高者为主风格，其余降级为 `element`（仅取色卡/母题），并在清单块注明 "image N provides palette accents only" |
| `style` 与 `layout` 冲突（版式要求不同） | `layout` 优先于 `style` 中的"版式骨架"表述；清单块中明确 "follow the composition of image X, but the colors of image Y" |
| 有 `character` 但 `lock_scope=style` | 二者的锁定语句**并存**（style 块 + character 块都写入），不互斥 |
| `custom` 与结构化角色重复 | `custom` 文本原样保留在清单块末尾，优先级最低 |
| `enabled=false` | 直接从数组剔除，**不占编号**（编号在装配时重排，保证 1..N 连续） |

### 5.3 编号稳定性约束（重要）
- 前端提交的 `ref_images` 数组**顺序即编号**；后端**严禁重排**。
- 装配器只做"过滤 disabled → 连续编号 → 生成 manifest"，不改变相对顺序。
- 降级到 L2 拼贴时，画布上的角标数字（1/2/3…）必须与 L1 的编号一致，导致 prompt 可复用同一套 manifest 文案。

## 6. API 契约（新增 / 变更）

### 6.1 `POST /api/upload_ref`（变更：支持多文件）
```
multipart/form-data
  files        多文件（重复字段名）   ← 新增
  file         单文件（兼容旧调用）   ← 保留
  images_dir   自定义图片目录（可空）
```
响应：
```json
{ "ok": true,
  "items": [
    {"filename":"ref_1736400000000_1.png","url":"/api/image/ref_1736400000000_1.png","size":823114,"sha1":"...","duplicated":false}
  ],
  "skipped": [ {"name":"a.gif","reason":"格式不支持"} ],
  "ref_image": "ref_..._1.png", "ref_url": "/api/image/..."   // 兼容字段：=items[0]
}
```

### 6.2 `GET /api/list_refs`（新增：参考图库）
```
query: images_dir（可空）
→ { "ok": true, "items":[ {filename,url,size,mtime,role,note,weight} ... ] }
```
数据源 = `masters/` 目录扫描 ∪ `masters/refs_index.json`（索引优先提供 role/note/weight）。

### 6.3 `POST /api/delete_ref`（新增）
```json
{ "filename":"ref_...png", "images_dir":"..." }
→ { "ok": true }
```
同步删除 `masters/refs_index.json` 中对应条目。**仅允许删除 `masters/` 内的文件**（走 `_validate_filename` + 目录校验）。

### 6.4 `POST /api/generate`（变更：多图 + 角色）
```json
{
  "openai_key":"...", "openai_base_url":"...", "model":"gpt-image-2",
  "prompt":"<页面提示词>",
  "ref_images": [
    {"filename":"ref_a.png","role":"style","weight":5},
    {"filename":"ref_b.png","role":"character","weight":4},
    {"filename":"ref_c.png","role":"element","weight":2}
  ],
  "ref_image": "ref_a.png",        // 兼容字段：老前端只传这一张
  "lock_scope": "style",
  "input_fidelity": "high",        // 新增，默认 high（有 ref_images 时）
  "size":"1920x1080", "quality":"high",
  "images_dir":"...", "project_name":"...", "index":3, "skip_proxy":false
}
```
兼容逻辑：若只收到 `ref_image`，则自动包装成 `ref_images:[{filename, role:(lock_scope==='face'?'character':'style'), weight:5}]`。

### 6.5 `POST /api/probe_edit_capability`（新增：能力探测，可选）
```
body: {openai_key, openai_base_url, model, images_dir, skip_proxy}
→ { "ok":true, "mode":"multi_image_array" | "multi_image_repeat" | "single_only" | "unknown",
     "max_images": 16, "probed_at": 1736400000, "cached": true }
```
探测方式：用 `masters/` 中两张最小尺寸的已有参考图（或内置两张 1×1 占位图）做一次极小尺寸（`low`+`1024x1024`）真实调用，分别尝试 `image[]` / `image` 重复 / 单 `image`，命中即缓存到 `~/.workbuddy`（或项目 `output/.capability.json`）。

### 6.6 `masters/refs_index.json`（元数据文件）
```json
{
  "schemaVersion": 1,
  "items": {
    "ref_1736400000000_1.png": {"role":"style","weight":5,"note":"","sha1":"...","addedAt":1736400000000}
  }
}
```
> 注意：该 JSON 与图片同目录不影响 `_find_image()`（按精确文件名查找）。

## 7. 降级策略（中转站兼容，核心工程点）

| 级别 | 策略 | 触发条件 | 保真度 | 成本 | 兼容性 |
|---|---|---|---|---|---|
| **L1** | 原生多图：重复 `image[]`（回退 `image` 重复） | 探测支持 | ★★★★★ | 1× | 低 |
| **L2** | 拼贴单图：N 张拼成 2×2/1×N 画布 + 角标，作为**单张** `image` 发送；prompt 说明 "panel 1..N" | 仅支持单字段但可传图 | ★★★☆☆ | 1× | 高 |
| **L3** | 仅主图：取 `weight` 最高、角色优先级最高的一张 | 上传多图但生成报错兜底 | ★★☆☆☆ | 1× | 最高 |
| **L4** | 串行链式：先用 ref A 生成 → 结果作为输入再叠 ref B → … | 明确需要多图且 L1/L2 都失败 | ★★★★☆ | N× | 中 |

**降级决策顺序**：`探测缓存 → L1 → (失败) L2 → (失败) L3 →（用户可选）L4`。
每次降级都**回传 `degraded_from` / `degraded_to`** 并在前端 toast 提示，避免"用户以为用了 4 张图，实际只用 1 张"。

**L2 拼贴细则**：
- 画布布局：2 张→左右；3~4 张→2×2；5~6 张→3×2；>6 张按上限截断。
- 每格等比缩放、留 8px 白边、右下角叠加序号角标（数字与 manifest 编号一致）。
- 单边不超过 2048px，整体 JPEG/PNG 质量 90，控制体积 < 10MB。
- **风险**：模型可能把拼贴的"分割线/角标"当画面元素生成出来 → 需在 prompt 中显式声明 "the reference is a contact sheet; the thin dividers and corner numbers are layout guides only, do NOT render them".

## 8. 前端交互设计（③ 卡片改造）

### 8.1 布局（改造后）
```
③ 参考图库 / 多参考图（可选，统一整批风格）

[ 拖拽到此上传，或点击选择多张 ]        支持 png/jpg/webp，单张 ≤10MB，最多 6 张（硬顶 16）
────────────────────────────────────────────────────────────
┌────────┬────────┬────────┬────────┐
│ 缩略图1 │ 缩略图2 │ 缩略图3 │ 缩略图4 │
│ #1 ★主  │ #2      │ #3      │ #4      │
│ 角色▾风格│ 角色▾人物│ 角色▾版式│角色▾素材│
│ 权重▾5  │ 权重▾4  │ 权重▾3  │ 权重▾2  │
│ [启用☑] │[启用☑] │[启用☐] │[启用☑] │
│ [删除]  │[删除]  │[删除]  │[删除]  │
└────────┴────────┴────────┴────────┘
────────────────────────────────────────────────────────────
锁定范围：( )整体风格 ( )仅人物   □ 使用 input_fidelity=high（更贵更稳）
中转站能力：[ 检测多图支持 ]  →  当前：原生多图 ✓ / 单图降级 ⚠
[ 清空参考图 ]   [ 从已生成图片添加 ]   [ 从参考图库选择 ]
```

### 8.2 交互要点
1. **多选上传**：`<input type="file" multiple>` + 拖拽区（`dragover/drop`），上传中显示占位骨架与逐张进度。
2. **缩略图卡片**：显示 `#序号`（前端 array 下标+1，**与提交顺序一致**）、角色下拉、权重下拉（1~5）、启用勾选、删除按钮。
3. **排序**：支持拖拽或上下箭头调整顺序；**顺序变化即编号变化**，需实时刷新 `#序号` 与清单预览。
4. **主图标记**：`weight` 最高者自动标 `★主`（L3 降级时用它）。
5. **清单预览**（可选但推荐）：折叠面板显示后端将拼出的 manifest 英文文本，用户可见即所得、可手动微调。
6. **从已生成图添加**：④ 页面图预览处现有「设为风格母版」改为「加入参考图」，弹出角色选择后追加，不再覆盖单值。
7. **单页覆盖**：④ 每页卡片新增「参考图」折叠区，默认为「继承全局」，可勾选本页专属子集。
8. **首图自动母版**：`auto_master` 逻辑改为 **append**（追加为 role=style, weight=5），而非覆盖 `state.refImage`。

### 8.3 状态与持久化变更
```js
state.refImages = [ {id, filename, url, role, weight, enabled, note} ];  // 取代 refImage/refUrl
state.refImage  = '';   // 只读兼容：= refImages 中 enabled 且 weight 最大者
state.capability = {mode:'unknown'}; // 探测结果缓存
```
- 历史记录 `schemaVersion: 2`：`workState.refImages` 数组；`doRestoreHistory()` 读到 `schemaVersion 1` 时把 `refImage/refUrl` 迁移为 `[{role:'style',weight:5,enabled:true}]`。
- `localStorage` 只存 `filename/role/weight/enabled/note/id`，不存 base64（体积控制）。

## 9. 边界、约束与安全

| 项 | 约束 |
|---|---|
| 数量 | 前端默认上限 **6**（可配），硬顶按模型 **16** |
| 体积 | 单张 ≤ **10MB**（API 硬限 50MB，留余量），单次总量 ≤ 40MB |
| 格式 | png / jpg / jpeg / webp；GIF/BMP/SVG 拒绝并给出原因 |
| 去重 | 上传时计算 SHA-1，命中 `refs_index.json` 则复用并提示"已存在" |
| 命名 | `ref_<毫秒时间戳>_<序号>.<ext>`，避免并发碰撞 |
| 安全 | 文件名一律过 `_validate_filename`；删除/读取校验目标在 `masters/` 内，防路径穿越 |
| 隐私 | 参考图仅存本地磁盘，不上传第三方（沿用现有原则） |
| 精确图表页 | `chart ∈ {radar,bar,pie}` 的页走 matplotlib，**跳过**参考图逻辑 |
| 并发 | 多图读取用 `with open()` 及时关闭句柄；`ThreadPoolExecutor` 下每条请求独立构造 files，不复用文件对象 |
| 超时 | edits 保持 `timeout=300`；L2 拼贴额外增加本地处理耗时（<1s） |
| 成本 | `input_fidelity=high` 更贵，前端需给明确提示；L4 链式 = N 倍费用，默认关闭 |
| prompt 长度 | manifest + 页面提示词合并后需 < 32000 字符（正常远低于） |

## 10. 与现有 A / B 链路的结合点

| 链路 | 结合点 |
|---|---|
| **A 链（手动逐页）** | ④「生成图片」携带 `ref_images`；③ 卡片是唯一的参考图集入口 |
| **B 链（文档一键）** | `parse_doc/outline/split_content/gen_prompts` **不变**；仅 `generateAll()` 时注入全局参考集 |
| **批量生图** | `generateAll()` / `retryFailed()` 两处调用 `generatePage()`，由 `generatePage()` 统一装配参考集，避免重复实现 |
| **首图自动母版** | 改造为 append 到 `refImages`，与手动上传共存 |
| **⑤ 生成 PPTX** | **完全不改**（`/api/build_ppt` 只吃图片文件名）；多参考图只影响"图上画什么" |
| **历史记录** | 升到 v2 并做 v1→v2 迁移 |

## 12. 验收标准与测试用例

**验收标准**
1. 一次可上传 ≥2 张参考图并生成，且生成结果同时体现"风格 + 人物"两类约束。
2. 关闭某张参考图的「启用」后，其**不占用编号**，manifest 编号连续。
3. 中转站仅支持单图时，系统自动降级到 L2/L3 并给出明确提示，**不静默失败**。
4. 老历史记录（v1）恢复后，原 `refImage` 变为 `role=style, weight=5` 的一张，可正常生成。
5. 精确图表页在有参考图时仍走 matplotlib，且不消耗生图额度。
6. `masters/` 中不存在索引里记录的孤儿文件时，`/api/list_refs` 不报错（以磁盘为准）。

**测试用例**
| # | 场景 | 预期 |
|---|---|---|
| T1 | 上传 3 张，分别设为 风格/人物/素材 | multipart 含 3 个图字段，编号 1/2/3，manifest 三段 |
| T2 | 上传 5 张，第 3 张禁用 | 实际发送 4 张，原第 4/5 张编号前移为 3/4 |
| T3 | 上传重名内容不同的文件 | SHA-1 不同 → 各存一份，命名带序号 |
| T4 | 重复上传同一文件 | 命中 SHA-1，提示"已存在"，复用原文件 |
| T5 | 中转站返回 400 unknown field `image[]` | 自动回退 `image` 重复；仍失败 → L2 拼贴 |
| T6 | 上传 GIF | 前端/后端拒绝并给出原因 |
| T7 | 上传 20MB 单图 | 拒绝，提示超限 |
| T8 | 文件名为 `../../etc/passwd` | `_validate_filename` 清洗，写入 `masters/` 内 |
| T9 | L4 链式（用户手动开启） | 按 weight 降序逐张 edit，费用 = N 倍，结果提示 |
| T10 | 恢复 v1 历史后再保存 | 快照为 v2，`refImages` 数组 1 项 |

## 13. 风险清单

| 风险 | 影响 | 缓解 |
|---|---|---|
| 中转站 multipart 实现不一致 | 多图失败 | 探测 + L1→L4 分级降级；字段名可配置 |
| 多参考图导致**指令互相打架** | 出图风格混乱 | 角色化 manifest + 冲突消解优先级 + 建议上限 6 张 |
| `input_fidelity=high` 成本上升 | 费用增加 | 默认仅在"有人物/锁长相"时开 high，其余 low；界面显式提示 |
| L2 拼贴把分割线画进画面 | 画面脏 | prompt 显式声明"分割线与角标仅为版式指引，不要渲染" |
| 大图上传阻塞 UI | 体验差 | 前端逐张上传 + 进度 + 体积校验前置 |
| 参考图集随项目迁移丢失 | 跨项目找不到 | 沿用现有 `_image_roots()` 跨目录查找；索引文件随 `masters/` 一起走 |
