现状诊断：问题不在「不好看」，而在「没体系」

基于现有 CSS 逐行核对

六个结构性缺口

  • 层次丢失：--bg #f4f6f9 与 --card #fff 只差 1.08:1；卡片内嵌区 #fafbfd 与白底只差 1.04:1 —— 等于没有内嵌层次，全靠描边硬撑。
  • 层级压缩：正文 14px、h3 也是 14px、h2 只有 16px。标题与正文只差 2px，扫读时找不到落点。
  • 令牌外泄：:root 只定义 12 个变量，但 CSS 里另有 16 处硬编码色值（#fafbfd ×6、#eff6ff ×3、#bfdbfe ×3 …），改动一处颜色要全局搜。
  • 形状不统一：圆角用了 12 / 10 / 8 / 20 / 50% 五套，阴影有 3 套互不相干的硬编码值。
  • 动效无语法：全站只写 transition:.15s（等价 all .15s）—— 连布局属性一起过渡，没有缓动曲线，也没有 prefers-reduced-motion 兜底。
  • 响应式只有一站：唯一断点 720px；表单网格靠 auto-fit 自动换列，拖动窗口时列数会突然跳变。

一处真实的无障碍缺陷

焦点环对比度不足：input:focus{outline:2px solid #bfdbfe} 与页面底色 #f4f6f9 的对比度仅 1.31:1，远低于 WCAG 2.2 要求的 3:1。键盘用户几乎看不见焦点在哪 —— 这不是审美问题，是可访问性缺陷。

同一个 #bfdbfe 也用在参考图选中态 .sm-card.selected 上，导致「已选中」这个关键状态同样难以辨认。

色彩体系优化

三层灰阶 · 语义成套 · 渐变克制
核心动作：先让「卡片」真的浮起来，再给卡片内部立层次。现状里画布 #f4f6f9 与卡片 #fff 只差 1.08:1，卡片内嵌区 #fafbfd 与白底只差 1.04:1 且没有描边 —— 每一层都在「靠自己」撑边界。方案把画布拉深到约 1.12:1，并新增 --surface-2（卡片内嵌区）、--surface-3（控件底 / 表头）两个中间层；光底主题里单靠亮度差不足以立层次，因此每一层同时给「亮度差 + 描边 + 圆角」三重界定。同时把散落的 16 处硬编码色值全部收编进令牌。

1.4 渐变：只用在两个地方

品牌渐变 · 135°
仅用于主按钮底与单个强调标题。两色明度差 ≤ 18%，是「同一块颜色被光扫过」，不是彩虹。
页面光晕 · radial
只在页面顶部铺一层 10% 透明度的单色光晕，给首屏一个视觉锚点，替代「纯色平底」的呆板。
明确不做：紫→粉色大渐变背景、每个元素都发光、彩虹色进度条。
渐变是调味不是主菜。三处以上渐变同时出现，界面立刻变成「AI 默认模板」的样子，品牌识别度归零。

落地路径与风险控制

四阶段推进，每阶段可独立验收
阶段一 · 令牌层（只加不改）

在 :root 里补齐全部新令牌（色彩 / 间距 / 圆角 / 阴影 / 时长 / 缓动），然后把 CSS 中散落的硬编码色值逐个替换为 var()。不改任何类名、不改 DOM 结构，因此不会影响 renderPages() 等拼接 HTML 的内联脚本。

风险：低。纯替换，可逐行 review。
阶段二 · 排版与间距

引入字阶、行高分级与 4pt 间距变量，调整卡片内距、标题间距、字段间距等纯数值属性。

风险：低。会影响卡片高度，但不影响功能；需要目视检查各卡片是否有意外的换行。
阶段三 · 组件与交互

统一圆角/阴影应用、新增 .card-hd 与 .badge 语义修正、按钮三态、焦点环、toast 与骨架屏动画。此阶段开始触碰 HTML 结构。

风险：中。改动 DOM 时须核对内联脚本中的 class 引用；.sm-card.selected、.badge.ok/err/run、.progress-wrap.show 这些被 JS 动态增删的类名必须保持原名，只做样式升级。
阶段四 · 响应式与适配

五级断点、容器查询表单网格、移动端工具栏堆叠、弹窗改底部抽屉。

风险：中高。需要真机或模拟器逐档验证；建议在 xs 档单独回归一遍完整流程（上传 → 生成 → 下载）。

必须遵守的三条红线

  • 不改 JS 动态引用的类名：.badge.ok / .badge.err / .badge.run / .sm-card.selected / .progress-wrap.show / .ref-card.off / .toast.show / .modal-mask.show —— 这些由 renderPages() 等函数写入，改名即断。
  • 不改 onclick 内联处理函数名：saveSettings() / addPage() / buildPpt() 等共 40+ 处，重构优先级低于样式。
  • 不改 localStorage 的存储键与数据结构：ppt_tool_history_v1 的 schemaVersion: 2 结构一旦变动，用户已有历史记录会全部读不出来。样式升级不要碰这一层。

回归验证

  • 每阶段结束后跑一次前端回归：node .workbuddy/ui_smoke.js —— 24 项断言覆盖 DOM 桩与内联脚本执行，能捕获「类名被改名」这类事故。
  • 拖拽窗口宽度逐档检查，重点看 600 / 900 / 1200 / 1440 四个拐点是否有意外换行、横向溢出或文字截断。
  • 三、四阶段之后各手动走一遍完整链路：解析文档 → 生成大纲 → 拆解文案 → 生成提示词 → 生成图片 → 生成 PPTX，并确认控制台无 pageerror。
  • 目视核对四处由 JS 动态改写的状态：徽标 ok / err / run、参考图选中态、按钮禁用与加载态、进度条显隐 —— 这几处最容易被「批量替换色值」改坏。
